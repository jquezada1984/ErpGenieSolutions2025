9. EVIDENCIA M3
============================================================

Archivo: gateway-api/src/services/almacenPython.js

CRUD:
- crearAlmacen / actualizarAlmacen
  → almacenFwdHeaders(req, payload) → ctxHeaders(req, body)
  Headers: X-Company-Id, X-User-Id, X-Scope-Acceso
  Empresa:
    GLOBAL: body.id_empresa || header || usuario.id_empresa
    EMPRESA: fuerza usuario.id_empresa
    sin usuario scope: header || body
  Usuario: X-User-Id del request entrante (cliente)

Writers stock:
- crearStockInicial, crearEntradaStock, crearSalidaStock,
  crearAjusteStock, crearTransferenciaStock,
  crearCambioMasivoStock
  → authenticatedWriteContext(req, payload)
  Identidad: Authorization Bearer → InicioNestJs `me`
  Ignora X-User-Id entrante como autoridad
  FAIL CLOSED 401/403/500 tipados
  Empresa según scope me + body (mismo patrón GLOBAL/EMPRESA
  pero anclado a JWT/me)

Python mitigación 10C (almacen_service.py + routes):
POST crear:
  X-Company-Id obligatorio (ValidationError)
  body.id_empresa si viene debe coincidir header
  body.id_empresa forzado = header
PUT actualizar:
  lookup find_almacen_by_id_and_empresa(id, header)
  cross-company → LookupError → 404 "Almacén no encontrado"
  body.id_empresa match header

Conclusión bypass:
  Con Python 10C vigente, la asimetría Gateway es
  principalmente DEUDA DE CONSISTENCIA de identidad
  (quién autentica usuario), no vía abierta trivial de
  escribir almacén en otra empresa vía body solo.
  Riesgo residual: ctxHeaders confía X-User-Id cliente
  + getUsuarioScope(id); authenticatedWriteContext no.
  Si Authorization y X-User-Id divergen, CRUD es más débil
  que writers.
