punta contra PostgreSQL real mediante pruebas controladas 3C–3F.

  - Replay idempotente sin escrituras.

6. FASE 3E — CONFLICTO IDEMPOTENTE
================================================================================

Request:
  Mismo id_origen
  Único cambio: cantidad 1.00 → 2.00

Resultado HTTP:
  409

Mensaje:
  Conflicto de idempotencia
  detail: La clave id_origen ya fue usada con otra intención

Persistencia:
  stock = 1 / stock_fisico = 1.00
  movimiento = 1 / cantidad = 1.000
  timestamps y auditoría sin cambios

Resultado 3E:
  CONFLICTO DE IDEMPOTENCIA CORRECTO.

7. FASE 3F — STOCK YA INICIALIZADO
================================================================================

Request:
  Nueva key f1f4e9ec-255e-4453-9969-0c08854e4776
  Mismo item + almacén
  cantidad 1.00
  referencia/concepto de prueba 3F

Resultado HTTP:
  409

Mensaje:
  Stock ya inicializado
  detail: El stock para item y almacén ya fue inicializado

Persistencia:
  stock = 1 / stock_fisico = 1.00
  movimientos del par item+almacén = 1
  movimientos con la nueva key = 0

Interpretación:
  Idempotencia (id_origen) y unicidad de saldo (item+almacén) son
  protecciones distintas. Nueva key no autoriza re-inicializar.

Resultado 3F:
  STOCK YA INICIALIZADO CORRECTAMENTE RECHAZADO.
  ROLLBACK del intento fallido = OK (sin movimiento huérfano).

================================================================================

Demostrado en 3C:

Demostrado en intentos fallidos previos (500 por schema) y en 3F:
  Fallo antes de commit / rechazo de negocio no deja filas parciales.

Invariantes de atomicidad del contrato:

  - Nunca saldo confirmado sin movimiento.
  - Nunca movimiento confirmado sin saldo (para STOCK INICIAL).
  - No hay commit intermedio en el writer.

15. INVARIANTES DEMOSTRADAS
================================================================================

INVARIANTE 1:
  Un item + almacén tiene máximo una fila de stock.
  Evidencia: 3C crea 1; 3D/3E/3F no crean segunda.

INVARIANTE 2:
  STOCK INICIAL genera exactamente 1 movimiento + 1 saldo.
  Evidencia: 3C.

INVARIANTE 3:
  Mismo id_origen + misma intención NO genera segunda escritura.
  Evidencia: 3D.

INVARIANTE 4:
  Mismo id_origen + intención diferente se rechaza.
  Evidencia: 3E (cantidad 2.00 → 409).

INVARIANTE 5:
  Nueva key + stock existente se rechaza.
  Evidencia: 3F.

INVARIANTE 6:
  Un error / rechazo de saldo no deja movimiento huérfano.
  Evidencia: 3F (nueva key = 0 movimientos).

INVARIANTE 7:
  Replay no modifica timestamps ni auditoría.
  Evidencia: 3D.
