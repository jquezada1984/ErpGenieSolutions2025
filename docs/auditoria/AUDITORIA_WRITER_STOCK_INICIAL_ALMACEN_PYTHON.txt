4. DRIVER, CONEXIÓN Y TRANSACCIÓN
================================================================================

Driver PostgreSQL:
  - SQLAlchemy mediante Flask-SQLAlchemy.
  - psycopg2-binary está declarado como dependencia.
  - DATABASE_URL tiene fallback postgresql://... en configuración.

Patrón de conexión:
  - No hay función de conexión, cursor manual ni context manager propio.
  - La conexión/sesión se obtiene mediante db.session de Flask-SQLAlchemy.
  - El ciclo de cierre de la conexión no se controla manualmente en los archivos
    del módulo; corresponde a la integración Flask-SQLAlchemy.

Patrón transaccional real:

  try:
    db.session.add(entity)
    db.session.commit()
  except Exception:
    db.session.rollback()
    raise

Esto aparece en create_almacen_row() y update_almacen_row() de
repositories/almacen_repository.py.

Conclusión:
  Existe patrón básico commit/rollback por operación de cabecera, pero NO existe
  todavía una transacción multi-entidad explícita para stock. La futura
  implementación debe extender el patrón existente a una sola db.session y un
  único commit final; no debe hacer commits intermedios.

Isolation:
  No hay configuración explícita en AlmacenPython. Para PostgreSQL, el default
  habitual es READ COMMITTED; la futura implementación debe verificar el
  entorno desplegado antes de depender de una configuración distinta. No se
  propone cambiarlo en esta fase.

7. VALIDACIÓN DIRECTA DE ITEM Y ALMACÉN
================================================================================

Item:
  AlmacenPython no posee un modelo Item local. ItemPython sí usa un modelo ORM
  y consultas SQL directas mediante db.session.execute(text(...)).

[RECOMENDADO]
  El writer futuro debe consultar public.item dentro de la misma db.session y
  transacción del writer, solicitando como mínimo:

    id_item, id_empresa, estado, inventariable, precio_compra

  Filtro conceptual:

    id_item = request.id_item
    AND id_empresa = request.id_empresa

  Después, aplicación valida:
    item existe;
    item.estado = true;
    item.inventariable = true.

Justificación:
  - evita una llamada de red innecesaria a ItemPython;
  - permite validar y escribir bajo la misma conexión/sesión;
  - el patrón ERP ya usa PostgreSQL compartido y db.session.execute(text(...))
    en ItemPython.

Almacén:
  AlmacenPython ya tiene modelo Almacen y find_almacen_by_id(), aunque este
  lookup actual no filtra empresa ni estado.

[RECOMENDADO]
  El writer debe usar una consulta específica dentro de su transacción que
  valide conjuntamente:

    id_almacen = request.id_almacen
    AND id_empresa = request.id_empresa
    AND estado = true

No reutilizar find_almacen_by_id() sin complementar filtros, porque no cubre
por sí solo multiempresa ni estado.

Multiempresa:
  La aplicación debe comprobar:

    request.id_empresa = item.id_empresa = almacen.id_empresa

  La BD refuerza la inserción del saldo mediante FKs compuestas. La validación de
  aplicación aporta respuesta clara y no debe depender únicamente del error FK.

8. id_origen E IDEMPOTENCIA USANDO SOLO TABLAS EXISTENTES
================================================================================

Índice existente confirmado por el contexto:

  uq_mov_inv_stock_inicial_idempotencia
  movimiento_inventario(id_empresa, modulo_origen, id_origen)
  parcial para modulo_origen='STOCK_INICIAL', tipo_movimiento='INICIAL' e
  id_origen no NULL.

[RECOMENDADO]
  El service recibe id_origen obligatorio para STOCK INICIAL, lo valida como UUID
  y consulta movimiento_inventario por:

    id_empresa = request.id_empresa
    modulo_origen = 'STOCK_INICIAL'
    tipo_movimiento = 'INICIAL'
    id_origen = request.id_origen

La consulta previa mejora la respuesta de retry, pero NO sustituye al índice:
dos transacciones pueden no ver una fila aún no confirmada.

Quién genera id_origen:
  No existe patrón real en AlmacenPython, ItemPython, InventarioPython ni
  BancoCajaPython para una clave idempotente de solicitud.

[PENDIENTE DE DECISIÓN]
  Definir el componente que genera y conserva el UUID durante retry. La única
  regla segura ya derivable es:

    AlmacenPython NO debe generar un UUID nuevo en cada retry.

El futuro contrato UI/API debe exigir que el caller autorizado preserve la misma
clave para la misma intención. Gateway debe transmitirla sin reemplazarla.

Retry válido:
  Si el movimiento previo existe y los campos comparables coinciden, retornar
  “ya procesado” junto con el resultado identificado, sin modificar saldo ni
  crear movimiento.

Payload diferente con misma key:
  Los campos existentes permiten comparar, sin crear fingerprint ni columnas:

    id_empresa
    id_item
    id_almacen
    tipo_movimiento
    modulo_origen
    cantidad
    fecha_movimiento
    referencia
    concepto

  Si cualquiera de esos campos de solicitud efectivos difiere después de
  normalizar Decimal/texto/null, responder conflicto de idempotencia. Son
  suficientes para STOCK INICIAL de una sola línea.

  costo_unitario y costo_total son resultado persistido de la primera
  ejecución, no deben recalcularse desde el precio_compra actual para decidir
  un retry: el precio del item podría cambiar después del commit y convertir
  erróneamente el mismo request en conflicto. Solo se comparan si un contrato
  futuro los recibe explícitamente como parte del payload.

Limitación documentada:
  movimiento_inventario no contiene referencia directa al id de saldo ni
  fingerprint de request. El resultado original debe obtenerse consultando por
  los datos persistidos existentes; si se necesitan comparaciones semánticas más
  complejas en el futuro, será una decisión posterior, no un cambio de este MVP.

9. CONCURRENCIA DE PRIMERA FILA
================================================================================

No confiar solo en:

  SELECT saldo
  si no existe → INSERT saldo

Dos solicitudes concurrentes pueden observar “sin fila”. La última defensa es:

  UNIQUE(id_item, id_almacen) de PostgreSQL.

Caso A y B con misma id_origen:
  - Ambas pueden no encontrar movimiento en la consulta previa.
  - Una insertará el movimiento INICIAL; la otra colisionará con
    uq_mov_inv_stock_inicial_idempotencia cuando la primera resuelva.
  - La transacción que recibe IntegrityError debe hacer rollback completo antes
    de releer el movimiento existente.
  - Si el payload coincide: devolver replay/ya procesado.
  - Si difiere: devolver conflicto de idempotencia.
  - Nunca crear ni aumentar un segundo saldo.

Caso A y B con id_origen distinta, mismo item+almacén:
  - Ambas pueden crear movimientos de forma no confirmada.
  - Solo una puede insertar stock_item_almacen por UNIQUE(id_item,id_almacen).
  - La perdedora recibe IntegrityError, realiza rollback completo y con ello se
    revierte también su movimiento insertado en la misma transacción.
  - Debe devolver conflicto controlado “stock ya inicializado”; nunca sumar,
    actualizar o considerar retry.

SELECT FOR UPDATE:
  - No es necesario para la PRIMERA inicialización: no existe fila de saldo que
    pueda bloquearse.
  - No sustituye UNIQUE para crear la primera fila.
  - Será útil en futuras operaciones que alteren una fila de saldo ya existente,
    pero no añade protección indispensable a este MVP.

No se recomienda añadir advisory locks ni SERIALIZABLE para STOCK INICIAL:
no hay patrón existente en el ERP y las dos constraints vigentes, la transacción
única y el manejo de IntegrityError cubren las dos carreras relevantes del MVP.

================================================================================
10. ORDEN TRANSACCIONAL RECOMENDADO
================================================================================

Opciones evaluadas:

A. INSERT movimiento → INSERT saldo
B. INSERT saldo → INSERT movimiento

[RECOMENDADO: A]

Motivo:
  - movimiento_inventario posee el índice idempotente ya aplicado;
  - intentar el movimiento primero hace que la clave de retry sea el primer
    recurso exclusivo de la transacción;
  - si otra solicitud con igual key llega concurrentemente, el índice impide que
    ambas continúen hacia el saldo;
  - si el saldo falla por su UNIQUE, el rollback elimina ese movimiento aún no
    confirmado, por lo que no queda historial huérfano;
  - no existe movimiento observable antes del commit.

Flujo técnico conceptual futuro:

  REQUEST
    ↓
  route: extraer body, X-Company-Id y X-User-Id
    ↓
  schema: UUIDs, Date, Decimal, cantidad > 0 y escala <= 2
    ↓
  service: validar contrato fijo INICIAL/STOCK_INICIAL
    ↓
  misma db.session / una transacción
    ↓
  consultar y validar item por empresa, activo e inventariable
    ↓
  consultar y validar almacén por empresa y activo
    ↓
  buscar movimiento previo por clave idempotente
    ├─ existe: comparar payload → replay o conflicto
    └─ no existe: continuar
    ↓
  construir costo con Decimal según contrato aprobado
    ↓
  INSERT movimiento_inventario (clave idempotente)
    ↓
  INSERT stock_item_almacen (stock_fisico=cantidad)
    ↓
  COMMIT único
    ↓
  RESPONSE creada

Si un INSERT genera IntegrityError:
  - rollback completo;
  - abrir/naturalmente usar una nueva transacción de lectura;
  - releer movimiento por idempotencia;
  - si existe, clasificar replay o conflicto de payload;
  - si no existe, clasificar la colisión de saldo como “stock ya inicializado”;
  - nunca continuar sobre una sesión en estado de transacción abortada.

11. ROLLBACK, UNIQUE VIOLATIONS Y ERROR MAPPING
================================================================================

Atomicidad:
  Todo debe estar en una única db.session con un único commit al final.

Fallo INSERT movimiento:
  - no se intenta confirmar saldo;
  - rollback deja cero cambios de la operación.

Fallo INSERT saldo después de movimiento:
  - rollback revierte el movimiento de la misma transacción;
  - no queda movimiento sin stock.

Fallo posterior a INSERT saldo y antes de commit:
  - rollback revierte saldo y movimiento;
  - no queda stock sin movimiento.

Patrón de errores existente:
  - ValidationError → 400.
  - IntegrityError → 409.
  - SQLAlchemyError → 500.
  - ValueError conocido puede mapearse a 409 o 400.

Recomendación de clasificación futura, sin fijar todavía endpoint:

| Error | Fuente principal | Categoría de respuesta |
|---|---|---|
| Item inexistente/empresa ajena | Validación service/consulta | negocio no encontrado o no autorizado |
| Item no inventariable/inactivo | Service | regla de negocio |
| Almacén inexistente/ajeno/inactivo | Service/consulta | negocio no encontrado o no autorizado |
| Cantidad <=0 o >2 decimales | Schema/service Decimal | validación |
| Mismo id_origen, mismo payload | Consulta movimiento | replay exitoso |
| Mismo id_origen, distinto payload | Consulta movimiento | conflicto idempotente |
| Colisión índice idempotente | IntegrityError + relectura | replay o conflicto idempotente |
| Colisión UNIQUE saldo | IntegrityError + ausencia de movimiento correspondiente | stock ya inicializado |
| Error inesperado DB | SQLAlchemyError | interno; rollback |

12. DECIMAL, COSTO Y FECHA
================================================================================

Decimal:
  AlmacenPython no manipula actualmente valores NUMERIC de stock.
  BancoCajaPython usa Decimal(str(valor)); ItemPython usa Decimal(str(value))
  para parsear valores. Ambos son referencias compatibles.

[RECOMENDADO]
  Schema y service futuros usan Decimal para cantidad, costo_unitario y
  costo_total. No usar float para cálculos ni comparaciones idempotentes.

precio_compra:
  ItemPython/models/item.py declara:

    precio_compra = Numeric(18,6), nullable

Contrato 2A:
  - precio_compra existente → costo_unitario;
  - NULL → 0.00.

Incompatibilidad/decisión pendiente:
  movimiento_inventario.costo_unitario es NUMERIC(15,2). Si precio_compra tiene
  tres o más decimales, falta una política aprobada de conversión. No se debe
  redondear ni truncar silenciosamente. Esto bloquea el writer hasta resolverse.

costo_total:
  En una fase posterior se calculará:

    cantidad × costo_unitario

  con Decimal y escala aprobada para NUMERIC(15,2). No se ejecuta cálculo ni
  escritura en esta auditoría.

Fecha:
  AlmacenPython usa datetime.now(timezone.utc) para auditoría de almacén;
  no existe operación de stock con fecha efectiva.

BancoCajaPython recibe fecha_movimiento desde el payload, validada como
fields.Date(required=True) para transferencias. Esta es la referencia más
próxima.

[PENDIENTE DE APROBACIÓN]
  Confirmar si STOCK INICIAL recibe fecha_movimiento del usuario o usa fecha de
  sistema. El writer no debe decidirlo por intuición.

Referencia y concepto:
  BancoCaja exige concepto para transferencia, pero no existe operación de
  inventario comparable. referencia y concepto son nullable en
  movimiento_inventario.

[PENDIENTE]
  No hay evidencia para hacer referencia obligatoria en STOCK INICIAL.

================================================================================
18. RIESGOS Y DECISIONES PENDIENTES
================================================================================

Riesgos controlados por la implementación futura:
  - SELECT previo sin constraint → carrera; se controla con UNIQUE BD.
  - sesión abortada tras IntegrityError → rollback obligatorio antes de releer.
  - dos keys sobre mismo item+almacén → UNIQUE saldo + rollback del movimiento.
  - retry con misma key → índice parcial existente + comparación de payload.
  - falta de Decimal → usar patrón BancoCaja/ItemPython.
  - modelo Almacen parcial: models/almacen.py usa String(36) y nullable=True
    para varios UUID/campos aunque la metadata vigente es más estricta; la
    consulta del writer debe validar explícitamente empresa y estado contra BD,
    no inferir garantías desde esa nulabilidad ORM.

Decisiones pendientes que bloquean el writer:
  1. Conversión de precio_compra Numeric(18,6) a costo_unitario Numeric(15,2)
     cuando hay más de dos decimales.
  2. Ownership y conservación de id_origen para reintentos.
  3. Fuente de fecha_movimiento.

Decisiones pendientes que no bloquean este diseño técnico:
  - obligatoriedad de referencia;
  - formato final de respuesta de replay/conflicto;
  - endpoint y permisos de exposición.
